# Kesher Article + Shorts Pipeline V4 Design

Date: 2026-09-03
Status: Proposed design, pending implementation

## Goal

Make the Kesher daily publishing pipeline reliably autonomous from article generation through a public YouTube Short, while removing unnecessary dependence on Jules for orchestration, Git repair, image handling, CI recovery, and publication decisions.

The core operating rule is:

> The article and the Short belong to the same controller-owned daily workflow, but they are separate publication stages. Once the article is live, Short failures may never roll back or block the article.

## Current Problems This Design Fixes

1. Article PRs can drift far behind `main`, accumulate unrelated commits, and become conflict-heavy.
2. Jules can generate or repair content correctly but is currently exposed to responsibilities that should belong to deterministic tooling.
3. Article publication file scope is duplicated across CI selector, validators, repair logic, and generated-output behavior. This caused real drift, including `public/rss.xml` being treated differently by different layers.
4. A PR may run the full CI profile and therefore skip the focused article gate, meaning the article-specific contract is not guaranteed to run on every article PR.
5. Image handling has had conflicting runtime semantics: canonical policy says image is required and publication-blocking, while a compatibility layer can defer image publication.
6. Local image fallback can select bytes already used by another article, or an asset with invalid dimensions, causing avoidable CI failures after commit.
7. GitHub `action_required` can represent a workflow-trigger condition rather than a content/code failure, but the automation does not consistently distinguish those cases.
8. The active NotebookLM pipeline produces a 16:9 90–180 second Video Overview and explicitly excludes Shorts, while the repository separately contains a 9:16 30-second `ArticleShort` composition. These are two different products today.
9. The canonical video contract says Jules review is advisory and technical validation is the publication gate, but compatibility code has historically drifted around that principle.

## Design Principles

### 1. One production contract

`config/kesher-production-contract.json` remains the single canonical policy source. Runtime adapters must not override its semantics.

Implementation will bump `contract_version` from 3 to 4 because the contract gains a distinct downstream Short stage and removes the image best-effort ambiguity. `controller_state_schema_version` will also move to 4 with an explicit migration from schema v3.

The implemented contract will explicitly state:

- controller owns orchestration, retries, recovery, and ordering;
- Jules owns article text generation and semantic text repair only;
- GitHub Actions owns deterministic PR normalization, generated indexes, image generation/fallback, CI, merge, deploy, and YouTube technical publication;
- article image is required before article merge;
- Short publication is downstream and cannot block an already-live article;
- Jules review of video remains advisory;
- technical verification is the blocking publication gate for the Short.

Compatibility fields may be derived in code, but may not redefine policy.

## Article Pipeline

### 2. Jules owns text only

The article worker starts from current `main` and asks Jules to create exactly one article for one Israel publication slot.

Jules must not:

- generate, download, copy, or modify image binaries;
- manage image provenance metadata;
- rebase branches;
- resolve Git conflicts;
- regenerate publication indexes manually;
- edit workflows, tests, package files, unrelated pages, or infrastructure;
- create a second PR when repairing an existing publication PR.

If a semantic repair is required, Jules edits only the new article text on the same PR branch.

### 3. Canonical Article Publication Contract

Create one shared Python module describing article publication paths and validation rules. All CI selector, normalizer, validator, and repair code imports this module instead of maintaining separate path lists.

Canonical publication outputs are:

- `src/data/posts.json`
- `src/data/postSummaries.json`
- `public/sitemap.xml`
- `public/rss.xml`
- `public/llms.txt` when generated by the current generator
- `public/llms-full.txt`
- exactly one referenced hero image under `public/images/generated/blog/`

Unknown or mixed paths force full CI, but they do not disable the article contract gate.

### 4. Article Normalizer / Auto-Repair

Before semantic Jules repair, deterministic automation normalizes every open `Publish Kesher article:` PR.

Inputs:

- current `main`;
- target publication slot;
- exactly one new article record extracted from the PR branch.

Process:

1. Read current `main` posts.
2. Identify the PR's one authoritative new article for the target slot.
3. Rebuild the publication branch from current `main` content semantics, preserving all existing articles exactly.
4. Insert only the target new article.
5. Regenerate `postSummaries`, sitemap, RSS, and llms outputs using repository generators.
6. Remove every path not permitted by the publication contract.
7. Preserve or attach the trusted hero image only through the image worker.
8. Push a clean fast-forward repair to the same PR branch.

The normalizer must safely handle the equivalent of the former #582 case: a branch with dozens of commits and 100+ changed files must reduce to the canonical publication diff without deleting articles already present in current `main`.

### 5. Semantic Jules Repair Only After Normalization

Jules repair is permitted only if the normalized PR still fails a semantic/content rule such as:

- word-count range;
- required structure;
- missing/weak headings;
- repetition;
- topic collision with recent articles;
- article-specific policy violations.

Image errors, Git conflicts, generated-output drift, CI trigger problems, and forbidden-file scope never consume a Jules content attempt.

## Image Pipeline

### 6. Image Is Required and Blocking for Article Merge

The canonical behavior is restored and made consistent: no article merges without one valid hero image.

Provider order remains:

1. Gemini
2. Unsplash
3. Pexels
4. local curated fallback

Before committing an image, the trusted worker validates:

- referenced path is local;
- minimum dimensions are 640×360;
- landscape orientation is appropriate for article use;
- actual SHA-256 matches declared evidence;
- SHA-256 does not collide with any existing article hero;
- imageAlt is concrete and valid;
- provenance/evidence fields match the chosen provider.

### 7. Collision-Safe Local Fallback

The local fallback must not simply copy the first category-matching asset.

It must:

1. inspect every candidate's dimensions and bytes before mutation;
2. reject candidates already used by any published article;
3. prefer topic-relevant unused assets;
4. if no suitable unused asset exists, create a deterministic visual variation from the best topic-relevant local source using trusted media tooling;
5. verify the resulting dimensions and SHA uniqueness before commit.

A failed candidate is rejected before branch mutation, not after CI.

## CI and Merge

### 8. Article Contract Gate Always Runs

Every PR whose title starts with `Publish Kesher article:` and modifies `src/data/posts.json` must run the article contract validator, regardless of whether the general CI profile is `article` or `full`.

The article gate verifies:

- exactly one new article;
- no existing article changed or disappeared;
- exactly one publication slot represented;
- canonical allowed publication paths only after normalization;
- generated outputs are consistent;
- text rules pass;
- hero image rules pass;
- PR head is reconciled against current `main` before merge;
- the `verify` status belongs to the exact current head SHA.

The general full CI continues to run whenever code, tests, workflow, package, or unknown paths are touched.

### 9. CI Trigger Recovery

`action_required` is never interpreted by itself as a human-approval requirement.

For the exact PR head:

- if a required job exists and fails, handle the real failure;
- if no job was created because an Actions-authored commit did not trigger the expected PR workflow, dispatch `ci.yml` explicitly against the exact head ref;
- wait for a fresh `verify` result on that exact SHA;
- never reuse a stale success from an earlier head.

### 10. Merge Ownership

The controller owns publication order. Auto-merge runs only after:

- normalization is complete;
- required image is valid;
- article contract gate succeeds;
- required repository checks succeed on the current head.

Jules does not decide merge readiness.

## Article Completion Boundary

### 11. Article Is Complete at Verified Live Publication

The article stage is complete when:

- PR is merged;
- deployment completes;
- canonical article URL returns HTTP 200;
- expected article title/content identity is verified publicly.

At that point article success is durable and irreversible from the perspective of downstream Short failures.

The controller records `article_live` before starting or resuming Short work.

## Shorts Pipeline

### 12. Short Is a Separate Downstream Stage

The daily state machine becomes conceptually:

`article_needed -> article_pr -> article_merged -> article_live -> short_needed -> short_running -> short_public -> complete`

If Short generation, Remotion processing, review, upload, or YouTube verification fails, state remains in a Short retry/backlog state. It never transitions the article back to an unpublished or failed state.

Old unresolved Shorts are processed FIFO without blocking the creation/publication of the next day's article.

### 13. Prefer Short-Specific NotebookLM Generation When Supported

Do not generate a 90–180 second horizontal Video Overview merely as an obligatory intermediate step.

Introduce a NotebookLM capability/preflight decision:

- if the installed NotebookLM CLI/provider supports a reliable short-form or sufficiently concise generation mode that preserves the required Hebrew narration quality, use it directly as `source_mp4`;
- otherwise use the existing NotebookLM Video Overview as source material and select one coherent segment for the Short.

This provider capability is discovered deterministically and recorded in state. The pipeline does not silently switch generators.

### 14. NotebookLM Remains the Narration/Source Master

The final Short must derive from NotebookLM output for the same exact article slug/content hash.

Remotion does not replace NotebookLM narration with separate TTS and does not generate a disconnected summary video.

Provider identity persisted before downstream work includes:

- article slug;
- article content SHA;
- NotebookLM source ID;
- generation task/artifact ID;
- raw source MP4 SHA.

### 15. Remotion Produces the Final 9:16 Short

Replace the current static-card interpretation of `ArticleShort` with a video-based vertical composition.

Final target:

- 1080×1920;
- 30–55 seconds target duration;
- original NotebookLM audio retained;
- one coherent idea from the article;
- dynamic crop/reframe from source video;
- minimal Hebrew branding and CTA;
- no generic subtitle layer;
- no alternate synthetic voice;
- no unrelated stock sequence that changes the semantic meaning.

If NotebookLM directly returns suitable 9:16 short-form video, Remotion may perform only branding/reframe/quality enhancement rather than segment extraction.

### 16. Segment Selection

When the source is longer than the desired Short:

1. transcribe the NotebookLM source in Hebrew;
2. map transcript timestamps to source duration;
3. select one contiguous, semantically coherent 30–55 second segment;
4. prefer a segment containing a clear hook/problem, one concrete insight, and a usable close;
5. reject selections that cut a sentence or depend on missing earlier context;
6. persist start/end timestamps and a segment-selection evidence hash.

Segment selection is deterministic/reproducible for the exact source artifact whenever possible.

### 17. Technical Publication Gate

A Short may upload when machine validation confirms:

- exact article slug and content hash match;
- exact NotebookLM provider/artifact identity is persisted;
- final MP4 exists and final SHA is persisted;
- final video is 9:16 within allowed tolerance;
- duration is within configured Short range;
- video and audio streams are valid;
- Hebrew transcript is present and sufficiently strong;
- final output is not a duplicate upload candidate;
- authenticated YouTube channel matches the Kesher channel;
- upload session and returned YouTube ID are persisted before later verification.

Jules review remains advisory. A technically valid Short is not blocked waiting for Jules.

### 18. Jules Video Review

Jules may review immutable evidence after technical validation:

- selected frames;
- transcript;
- source identity;
- final metadata.

A Jules visual rejection may request one Remotion rebuild of the exact same NotebookLM source artifact. It may not trigger a second semantic generation automatically unless the technical controller decides the source itself is invalid.

A late advisory rejection after publication becomes a repair recommendation, not retroactive publication failure.

## YouTube and Idempotency

### 19. One Short Per Article

Identity key:

`article slug + article content SHA`

For that identity there may be only one active publication chain and one authoritative public YouTube result.

Retries must resume persisted provider IDs, artifact IDs, upload-session URI, or YouTube ID when available.

No retry creates a second YouTube insert merely because verification was interrupted.

### 20. Public Verification

Short completion requires YouTube API verification of:

- exact expected channel;
- privacy status `public`;
- processing status succeeded;
- persisted YouTube ID and URL.

Only then does the controller mark `short_public` / daily `complete`.

## State and Recovery

### 21. State Schema V4 and Separate Durable Article/Short Success

Controller state schema v4 preserves independent stage status. At minimum:

- article identity and live verification;
- article PR/run/image identities;
- Short source provider identity;
- Short source mode (`direct-short` or `overview-segment`);
- Remotion output identity;
- selected segment timestamps/evidence when applicable;
- YouTube upload/verification identity;
- attempt counts by stage;
- retry timestamps;
- failure fingerprints;
- backlog entries.

Schema-v3 migration must preserve all known article/image/video provider identities, retry history, and unresolved work. A v3 item must never disappear merely because v4 changes the final product to a Short.

Cycle rollover must never lose unresolved Short work from earlier dates.

### 22. Legacy Video Overview Migration

Existing public YouTube videos remain untouched.

Existing unresolved NotebookLM Video Overview items are migrated as follows:

- if the exact NotebookLM source/artifact identity and raw MP4 are recoverable, the item becomes a legacy `overview-segment` Short source and is converted to the new 9:16 final product;
- if the artifact can be re-downloaded from persisted provider identity, recovery may redownload it and then convert it;
- unresolved legacy Overview items are not uploaded automatically as new long-form videos after v4 activation;
- if provider identity is incomplete or unrecoverable, preserve an auditable terminal legacy state and allow newer article/Short work to continue instead of globally blocking production;
- no migration creates a second YouTube upload for an article that already has a verified authoritative public result.

### 23. Heartbeat Is Recovery Only

Normal progress remains event-driven through workflow completion and pushes.

The 15-minute controller heartbeat is only for:

- missed event recovery;
- provider polling/resume;
- retry after backoff;
- resuming persisted YouTube verification;
- recovering a clean PR whose CI dispatch was missed.

A heartbeat does not create duplicate semantic work.

## Migration Strategy

### Phase A — Article Reliability First

Implement and verify:

- production contract v4 article semantics;
- shared article publication contract module;
- RSS alignment;
- deterministic normalizer/repair;
- always-on article validator;
- exact-head CI dispatch recovery;
- strict image-blocking semantics;
- collision-safe image fallback;
- tests reproducing dirty/behind/conflicting article PRs.

No Short behavior changes ship in this phase.

### Phase B — Short Production

Implement:

- NotebookLM short capability probe;
- source-mode selection (`direct-short` or `overview-segment`);
- video-based 9:16 Remotion composition;
- segment selection;
- Short technical gate;
- advisory Jules evidence path;
- YouTube idempotent upload and verification.

### Phase C — Controller Integration and State Migration

Implement schema-v4 migration and orchestration so that:

- article completion is independent;
- Short starts only after `article_live`;
- unresolved Shorts form FIFO backlog;
- Short failure does not block next article;
- exact identities survive retries and cycle rollover;
- legacy unresolved Video Overviews migrate to Short source work when recoverable.

### Phase D — End-to-End Validation

Run controlled production-like tests including:

1. clean article PR;
2. deliberately dirty article PR with forbidden files;
3. branch behind `main` with newer articles already merged;
4. duplicate/invalid local image candidate;
5. Actions-authored commit requiring explicit CI dispatch;
6. successful article publication followed by forced Short failure;
7. Short recovery without article rollback;
8. interrupted YouTube upload/verification resumed without duplicate insert;
9. migration of one recoverable unresolved legacy Overview;
10. successful public Short verification.

### Phase E — Simplify Compatibility Layers

Only after the new path is proven stable:

- remove obsolete `best_effort` policy overrides;
- collapse duplicate controller compatibility adapters where tests prove behavior parity;
- retain one canonical production controller entrypoint.

This cleanup is not a prerequisite for Phase A or B and must not be combined with them if it increases deployment risk.

## Testing Strategy

Required automated coverage includes:

- unit tests for shared article path classification;
- unit tests for normalizer preserving all base articles;
- unit tests that a #582-style dirty branch reduces to canonical scope;
- image SHA/dimension collision tests;
- CI exact-head status tests;
- contract tests proving image is blocking and Jules video review is advisory;
- state-machine tests proving Short failure cannot undo `article_live`;
- FIFO Short backlog tests;
- schema-v3 to v4 migration tests;
- recoverable and unrecoverable legacy Overview migration tests;
- NotebookLM direct-short capability/fallback tests;
- Remotion output geometry/duration/audio-preservation tests;
- upload idempotency tests with persisted upload session and YouTube ID;
- recovery tests across controller heartbeat and cycle rollover.

## Non-Goals

- Replacing Jules as article writer.
- Replacing NotebookLM narration with another TTS engine.
- Publishing both a long Overview and a Short for every article by default.
- Rewriting the entire controller stack before the new path is proven.
- Making visual Jules review a publication blocker.
- Allowing article publication without a validated hero image.
- Deleting or replacing already-public legacy videos solely to adopt v4.

## Definition of Done

The design is complete in production when an operator can start from current `main`, allow Jules to produce one daily article, and make no manual intervention while the system autonomously reaches:

1. one clean article PR;
2. one valid unique hero image;
3. green article and repository gates;
4. merge and live public article verification;
5. one downstream NotebookLM-derived 9:16 Short;
6. technical validation;
7. one public processed YouTube upload;
8. durable complete state.

Additionally, a deliberately dirty or stale article PR must repair itself without Jules performing Git surgery, and a deliberately failed Short must retry or backlog without affecting the already-live article or blocking the next day's article publication.
